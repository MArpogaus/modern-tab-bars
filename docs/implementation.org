#+TITLE: How modern-tab is built
#+OPTIONS: toc:nil

Three files.  =modern-tab.el= holds what both modes draw with and is
the main one; =modern-tab-bar.el= dresses the tab bar and
=modern-tab-line.el= dresses the tab line.

The package is =modern-tab=, after that main file, and every symbol
carries the same prefix: package-lint takes the prefix from the main
file, elpaca reads the version and the dependency line from the file
the id names, and both are that one file.  The repository is named
=modern-tabs= because it holds the two rows of tabs Emacs has; a
recipe names the two separately, so the difference costs nothing.

There is no entry file.  Both modes are autoloaded, so a reader who
installs the package can name them in a hook without requiring
anything, and the file whose only body was two =require= forms is
gone.

* The indicator

The bar beside a tab is a PBM image of one colour, built once per
height, width and colour and kept in a hash table.  Building one means
a fresh payload string and a spec the image cache then compares whole,
and a row of tabs is built again on every command.

A frame without images — a terminal, or one built without PBM — draws
one column of =|= instead.  The face is only put on where a colour was
given: a face attribute of nil is not "leave it alone", it is an error
the display logs on every redisplay.

Each mode names an option per state: a width and a colour for the
selected tab, a width and a colour for the others.  The two modes name
them the same way, so a reader who has set one knows how to set the
other.

* Icons, and what a frame can draw

=modern-tab-glyph= takes candidates, best first.  A graphic frame
shows the first one as it is: which fonts draw a character — the face's
own, or a fallback the fontset finds — is the frame's business, and a
version that refused fallback fonts refused the reader's =✕= and every
nerd glyph with it.  The candidate list exists for terminals.

A terminal has no font to ask.  =char-displayable-p= answers for the
coding system there, and a UTF-8 terminal says yes to every character
it can encode, box or not.  So a character of a Unicode private use
area is refused on a terminal — that is where a nerd font keeps its
glyphs, and no terminal font can be assumed to carry them — and the
first candidate that passes whole wins, the last one being the answer
where none does.  Every character is asked about, not the first one
alone: the glyphs are padded with spaces, and a question about the
first character was a question about a space.

Finding a nerd icon walks the table of its style — 6880 entries for the
material design one — so an answer is kept per key and per kind of
display.  A terminal and a graphic frame answer differently and one
session can hold both, which is why the kind of display is part of the
key.  Every glyph is chosen at draw time and none at enable time: a
daemon enables its modes with no frame at all, and one session can hold
a terminal frame and a graphic frame together.  The table is emptied
when a font arrives (=after-setting-font-hook=) and when an option an
icon depends on is set; emptying it also clears the =tab-line-cache=
parameter of every window, which is where a row already drawn is kept.

* What a mode gives back

Both modes set variables that belong to Emacs, and both put back what
they found.  =modern-tab-borrow= keeps the value of each variable under
the name of the mode before the mode sets it, and =modern-tab-give-back=
writes those values back.  It keeps nothing for a mode that has
borrowed already: =define-minor-mode= runs its body on every call, and a
mode enabled twice would otherwise record the values it set itself.

=custom-reevaluate-setting= was the restore before this, and it is the
wrong tool twice over.  A plain =defvar= has no standard value, so it
was set to nil — =tab-line-close-button= came back as nothing and the
stock tab line lost its close button.  And a value the reader had set
with =setq= was thrown away for whatever the custom file said.

Neither mode sets a button of Emacs any more.  The tab bar draws its
own buttons from its format, and the tab line binds
=tab-line-close-button= while it formats a tab.  A button settled at
enable time is settled for one kind of display, and a daemon enables
its modes with no frame at all.

* The tab line hides itself

A row of tabs with a single tab on it says nothing and costs a line of
every window, so a window showing one buffer gets =tab-line-format= of
=none= as a window parameter.  The tabs of a window come from the two
buffer lists of that window, so three hooks keep the parameter current:

- =window-buffer-change-functions=, for a window that shows another
  buffer;
- =window-configuration-change-hook=, for the windows themselves
  changing;
- =kill-buffer-hook=, for a buffer that leaves the buffer lists of the
  windows that remember it.

The last one is the only word of a killed buffer that no window shows:
nothing about a window changes, so no window change function runs.  It
runs before the buffer goes, which is why the count discounts the tab
of the buffer that is going.

A window is re-decided only where the hiding was this package's own.
The =none= it sets leaves the =modern-tab-line-hide= parameter behind
as the mark of its own, and a later decision touches a window only
where the mark is there.  The =none= another package sets —
=auto-side-windows= hides the side panels of a frame this way — is not
undone, and a row stays off a panel that wanted it off.

=buffer-list-update-hook= was here before.  It runs on every
=get-buffer-create=, =set-buffer= and =kill-buffer= — about twice per
buffer operation — and each run walked the buffer lists of a window for
a count that had not changed.

Turning the mode off takes the parameter off every window of every
frame, and only where the mode had borrowed: a mode that was never on
hid no row.

* The tab bar in a terminal

A terminal paints the tab bar row in the redisplay that turns the bar
on.  With a menu button in the format, a tab that changes before that
redisplay leaves the row blank for the rest of the session, and neither
=force-mode-line-update= nor =redraw-display= brings it back.  Measured
with Emacs 30.2, in tmux 3.7 and under pyte.  So the entry that draws
the menu button answers with nothing on a terminal; =M-`= reaches the
menu there in any case.  The entry stays in the format and answers per
redisplay, so a daemon answers for each of its frames.

The spacers are the same story.  A =space-width= display property
paints no part of a cell in a terminal, and one such item in the format
leaves the whole row unpainted, still showing what stood in it before.
So the spacers answer with nothing there too.

* Complexity

The =elisp-complexity= pre-commit hook reports the cognitive complexity
of every function, counted the way SonarSource defines it: a branch
costs one, a branch inside a branch costs one plus its depth, a
sequence of =and= or =or= costs one, and a straight line costs nothing.
The number says how much a reader has to hold in their head, and 15 is
where a function is worth a second look.
